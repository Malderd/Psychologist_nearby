\# ADR-001. Выбор технологического стека проекта «ПсихологРядом»



\*\*Автор:\*\* Куликов К. Д.



\*\*Статус:\*\* принято после согласования участниками проекта.



\*\*Дата оформления:\*\* 24.11.2026.



\## 1. Контекст



Необходимо разработать веб-приложение для практикующего психолога, обеспечивающее регистрацию и авторизацию пользователей, прохождение психологических тестов, просмотр результатов и запись на консультации.



При выборе технологического стека учитываются возможность командной разработки, поддержка баз данных, наличие инструментов тестирования, отладки и автоматической сборки, а также возможность запуска приложения вне среды разработки.



\## 2. Рассмотренные альтернативы



\*\*Вариант 1. C#, ASP.NET Core и Blazor Server.\*\*



Преимущества:



\- использование C# для серверной логики и интерактивных компонентов интерфейса;

\- встроенная поддержка внедрения зависимостей;

\- интеграция с Entity Framework Core;

\- возможность разработки и отладки в Visual Studio;

\- поддержка автоматической сборки и тестирования средствами .NET CLI.



Недостатки:



\- необходимость постоянного соединения с сервером для интерактивных компонентов;

\- зависимость от установленной среды выполнения при framework-dependent поставке.



\*\*Вариант 2. ASP.NET Core Web API и React.\*\*



Преимущества:



\- разделение клиентской и серверной частей;

\- возможность независимой разработки интерфейса и API.



Недостатки:



\- необходимость использования дополнительного технологического стека JavaScript или TypeScript;

\- усложнение сборки, тестирования и взаимодействия компонентов;

\- увеличение трудозатрат небольшой команды.



\## 3. Принятое решение



Для проекта выбран следующий технологический стек:



\- язык программирования — C#;

\- целевая платформа — .NET 8.0;

\- веб-фреймворк — ASP.NET Core Blazor с интерактивным серверным режимом;

\- база данных — MySQL;

\- доступ к данным — Entity Framework Core и Pomelo.EntityFrameworkCore.MySql;

\- среда разработки — Visual Studio;

\- управление зависимостями — NuGet;

\- система контроля версий — Git и GitHub;

\- автоматизация сборки и тестирования — GitHub Actions.



Выбор обусловлен возможностью реализации интерфейса и серверной логики с использованием единой платформы .NET, сокращением сложности разработки и наличием инструментов контроля качества.



\## 4. Модель исполнения



Исходный код C# компилируется средствами .NET SDK и MSBuild в управляемые сборки, содержащие промежуточный код CIL.



При запуске приложения среда выполнения CLR обеспечивает выполнение управляемого кода, JIT-компиляцию, управление памятью и обработку исключений.



Приложение выполняется на сервере ASP.NET Core. Пользователь взаимодействует с ним через браузер. Интерактивные компоненты Blazor выполняются на сервере, а взаимодействие с браузером обеспечивается посредством SignalR.



Для разработки используется конфигурация Debug и среда Development. Для подготовки поставки используется конфигурация Release. При проверочном запуске опубликованного приложения явно устанавливается среда Production.



\## 5. Последствия принятого решения



Положительные последствия:



\- единый технологический стек;

\- возможность модульного тестирования;

\- автоматическое восстановление зависимостей;

\- поддержка автоматизированной сборки;

\- возможность публикации и запуска приложения вне каталога исходного кода.



Ограничения:



\- необходимость наличия совместимой среды выполнения .NET при зависимой от платформы поставке;

\- необходимость настройки подключения к базе данных;

\- необходимость контроля состава публикуемых файлов;

\- зависимость интерактивного интерфейса от соединения с сервером.



\## 6. Способ проверки решения



Проверка осуществляется посредством:



\- сборки приложения в конфигурации Debug;

\- запуска приложения из Visual Studio;

\- публикации приложения в конфигурации Release;

\- запуска опубликованной сборки из отдельного каталога;

\- сравнения состава артефактов и фактического вывода;

\- проверки расположения и доступности файла reglament.txt;

\- выполнения автоматических проверок GitHub Actions.



Результаты проверки фиксируются в отчёте о практической работе.
