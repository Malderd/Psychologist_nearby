# ADR-003: Повторное использование SMTP-клиента в EmailSender

**Автор:** Куликов Константин  
**Дата:** 23.11.2026  
**Статус:** Ограничить применение

## 1. Контекст

В проекте Psychologist_nearby используется модуль EmailSender,
предназначенный для отправки электронных писем, в том числе кодов
подтверждения входа пользователя.

В базовом варианте SMTP-клиент создаётся отдельно для каждой
операции отправки.

В рамках практической работы №4 была исследована альтернативная
организация исполнения, при которой один экземпляр SmtpClient
повторно используется для нескольких последовательных отправок.

## 2. Гипотеза

Предполагалось, что повторное использование экземпляра SmtpClient
уменьшит медианное время отправки электронного письма не менее чем
на 20% относительно базового варианта.

Гипотеза считается недостаточно подтверждённой для безусловного
внедрения в производственный модуль, если результат зависит от
сетевых условий и не подтверждён дополнительными измерениями.

## 3. Рассмотренные варианты

### Вариант A — базовый

Создание нового экземпляра SmtpClient для каждой отправки.

Преимущества:
- простая организация жизненного цикла объекта;
- изолированность отдельных операций отправки;
- отсутствие общего экземпляра клиента между вызовами.

Недостатки:
- повторное создание объекта;
- потенциально дополнительные накладные расходы.

### Вариант B — альтернативный

Создание одного экземпляра SmtpClient и его повторное использование
для нескольких последовательных отправок.

Преимущества:
- уменьшение медианного времени в проведённом эксперименте;
- сокращение повторных операций создания SMTP-клиента.

Недостатки:
- необходимость контролировать жизненный цикл клиента;
- необходимость учитывать последовательность и конкурентность вызовов;
- требуется дополнительная проверка в условиях реального приложения.

## 4. Данные эксперимента

Результаты базовой линии P5:

- Min: 1815,33 мс;
- Median: 2274,24 мс;
- Max: 2578,90 мс;
- относительный разброс: 33,58%.

Результаты альтернативного варианта P6:

- Min: 751,32 мс;
- Median: 904,82 мс;
- Max: 1338,71 мс;
- относительный разброс: 64,92%.

Изменение медианного времени:

- абсолютное сокращение: 1369,42 мс;
- относительное сокращение: 60,21%.

Протоколы измерений и снимки экрана P5 и P6
сохраняются в материалах практической работы №4.

## 5. Архитектурный вердикт

Решение: ограничить применение альтернативного механизма.

Альтернативный вариант показал существенное уменьшение медианного
времени отправки в экспериментальной среде.

Однако относительный разброс P6 составил 64,92%, а измерения
проводились в отдельном консольном эксперименте.

Поэтому результат не является достаточным основанием для
безусловного изменения производственной архитектуры EmailSender.

Повторное использование SMTP-клиента допускается рассматривать
для последовательных операций отправки после проверки корректности,
жизненного цикла объекта и поведения при конкурентных вызовах.

## 6. Границы применимости

Полученный результат относится к следующим условиям:

- SMTP-сервер smtp.mail.ru;
- порт 587;
- SSL включён;
- тестовые письма одинакового содержания;
- две прогревочные отправки;
- пять измерительных отправок;
- последовательное выполнение операций;
- оборудование и сетевые условия, использованные при эксперименте.

Результат не следует автоматически переносить на другие SMTP-серверы,
другие сетевые условия и конкурентную отправку писем.

## 7. Цена решения и риски

При внедрении повторного использования SMTP-клиента необходимо
учитывать:

- управление временем жизни объекта;
- корректное освобождение ресурсов;
- обработку ошибок подключения;
- поведение при нескольких одновременных отправках;
- необходимость повторного измерения производительности.

## 8. Способ проверки

Для окончательной проверки решения необходимо:

1. Внести изменение в производственный EmailSender.
2. Проверить корректность отправки тестовых писем.
3. Выполнить модульные и интеграционные тесты.
4. Провести повторные измерения в Release.
5. Сравнить результаты с базовой линией P5.
6. Проверить поведение при нескольких одновременных запросах.
7. Пересмотреть ADR при получении новых данных.

## 9. Условия пересмотра

Решение пересматривается, если:

- повторные измерения подтвердят устойчивое сокращение времени;
- разброс результатов станет приемлемым;
- проверка в производственном модуле подтвердит корректность;
- будут выявлены проблемы при конкурентной отправке.
