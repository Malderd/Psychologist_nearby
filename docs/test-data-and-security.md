# Исходное состояние и ранние ограничения безопасности — Psychologist_nearby

Связано с [requirements.md](requirements.md) (FR-01…FR-16, NFR-01…NFR-05).

## 1. Как проверяющий получит нужное состояние

Состояние на дату подготовки: проект собирается, работает регистрация и вход на шаблоне ASP.NET Core Identity, таблиц предметной области (заявки, тесты, записи) ещё нет. Всё остальное в таблице описывает план.

| Что | Как получить |
|---|---|
| Исходный код и запуск | Клонировать репозиторий `https://github.com/Malderd/Psychologist_nearby`, установить .NET 8 SDK, выполнить `dotnet restore` и `dotnet run` в папке проекта `Psychologist_nearby` |
| База данных | Структура создаётся миграциями EF Core, реальных данных клиентов в репозитории нет. Сейчас код использует SQL Server (LocalDB), README указывает MySQL |
| Учебные учётные записи | Клиент A, клиент B и психолог, создаются скриптом начального наполнения (планируется); пароли в репозитории не хранятся, а задаются через user-secrets или переменные окружения |
| Почтовая служба (код входа) | Учебный режим (планируется): в среде разработки письма перехватывает локальный тестовый SMTP-сервер, чтобы проверка не зависела от личной почты разработчиков; в рабочей среде такой режим отключён |
| Методика теста | Пока не передана заказчиком (OQ-01); до получения в тестовых данных используется условная учебная схема подсчёта, помеченная как заглушка |
| Место размещения | Неизвестно (OQ-14); проверка выполняется локально |

**Набор тестовых данных** (синтетические, покрывает критерии из `specification.md`):

- клиент A (`Тест Клиент`, `+0 000 000-00-00`), клиент B и психолог (FR-03, FR-08);
- ответы теста: все вопросы, на один вопрос меньше (FR-06), минимальный, максимальный и граничные значения порогов (FR-07);
- профиль: пустое имя, телефон `abc`, корректные данные (FR-04);
- расписание: слоты 10:00–19:00, занятый слот (FR-09, FR-10), день с четырьмя записями (FR-11), запись через 2 часа и через 1 час (FR-12);
- клиент в статусе «пробное прошло» (FR-14);
- две заявки с одним телефоном для удаления дубля (FR-13);
- сценарии ошибок: нет свободных слотов, остановленная БД, неотправленное письмо (FR-16).

**Для будущих проверок:** 20 клиентов и 70 записей для замера отклика (NFR-05); тест шифрования и расшифровки (NFR-02); проверка одноразовости и срока действия кода (NFR-04); автотест с двумя параллельными запросами на один слот (FR-10).

## 2. Ранние ограничения безопасности

| Вопрос | Ответ |
|---|---|
| Что важно сохранить или ограничить | Результаты теста (сведения о психологическом состоянии клиента); имя, телефон и email; записи и статусы; пароли и коды входа; ключ шифрования, строка подключения, пароль почтовой службы |
| Откуда приходит недоверенный ввод | Поля регистрации, входа и профиля (email, пароль, имя, телефон, Telegram); код из письма; ответы теста; выбор слота (идентификатор, дата и время); идентификаторы записей и результатов в запросах страниц |
| Кто должен иметь доступ к существенным действиям | Клиент — только к своим данным, результату, записи и отмене; психолог — к расписанию, заявкам, результатам клиентов и удалению дублей; БД — только приложению; разработчики работают с учебной базой, без реальных данных клиентов |
| Реалистичный ущерб | Раскрытие результатов тестов и контактов клиентов; чужой доступ к аккаунту (блокировки после неверных попыток заказчик не потребовала, поэтому подбор пароля смягчается только кодом из письма); двойная запись на одно время; утечка ключа или пароля через репозиторий; потеря данных при сбое; обработка персональных данных без согласия клиента |
| Где хранится конфигурация с секретами и что нельзя выводить в журнал | user-secrets при разработке и переменные окружения на сервере, не в Git; `appsettings.json` содержит только несекретные значения. В журналы и сообщения об ошибках не выводятся пароль, код входа, телефон, email и ответы теста |

## 3. Планируемая проверка

Проверки ниже планируются и пока не выполнялись.

| Требование | Когда и как проверим |
|---|---|
| NFR-01 | Поиск секретов в репозитории (`git grep`) и review при каждом PR, повторно перед сдачей |
| NFR-02 | После реализации шифрования: прямой просмотр столбцов БД и тест шифрования с расшифровкой |
| NFR-03 | После реализации ролей: запрос чужого результата клиентом и неавторизованный запрос должны вернуть отказ; в БД нет паролей в открытом виде |
| NFR-04 | Автотест кода входа: повторное использование и просроченный код отклоняются |
| FR-10 | После реализации записи: автотест с двумя параллельными запросами на один слот, создаётся ровно одна запись |
| FR-16 | После реализации: прогон трёх сценариев ошибок (нет слотов, остановленная БД, неотправленное письмо) |
