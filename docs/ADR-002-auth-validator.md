# ADR-002. Заменяемость логики валидации данных

**Автор:** Куликов К. К. 
**Статус:** принято

## 1. Контекст
В приложении Psychologist_nearby логика проверки email, паролей и телефонов была реализована в виде статического класса `AuthValidator`. Потребители (Razor-страницы) напрямую вызывали статические методы. Это затрудняло написание модульных тестов для страниц (UI) и не позволяло подменить логику валидации на упрощенную для демонстрационных целей.

## 2. Рассмотренные варианты
**Вариант 1. Оставить статический класс.**
*   *Плюс:* Минимальные изменения.
*   *Минус:* Невозможно подменить реализацию, тесты жёстко привязаны к логике.

**Вариант 2. Выделить интерфейс `IAuthValidator` и внедрять его через DI.**
*   *Плюс:* Потребители зависят от контракта, а не от реализации. Легко подменить реализацию в `Program.cs`.
*   *Минус:* Дополнительный интерфейс и небольшой boilerplate-код.

## 3. Решение
Выделен интерфейс `IAuthValidator`, созданы две реализации: `RegexAuthValidator` (основная) и `FixedAuthValidator` (тестовая). Внедрение осуществляется через DI (`builder.Services.AddScoped<IAuthValidator, RegexAuthValidator>()`).

## 4. Последствия
*   **Цена решения:** Создан дополнительный файл интерфейса. Потребителям добавлена строка `@inject`.
*   **Выгода:** Код потребителей не зависит от реализации. Можно легко переключаться между валидаторами, меняя одну строку в `Program.cs`.

## 5. Способ проверки
Запуск сценария регистрации с `FixedAuthValidator` (всегда возвращает успех). Если UI работает корректно, значит, подмена выполнена успешно.
